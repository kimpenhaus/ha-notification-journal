# Development

How Notification Journal is built, tested and deployed. For what it does and how to use it, see the [README](../README.md).

## Commands

| Task | Command |
|------|---------|
| Install tools | `python3 -m pip install -r requirements-dev.txt` |
| Lint | `ruff check . && ruff format --check .` |
| Tests | `python3 -m pytest` (needs the frontend wheel: `scripts/install-test-requirements.sh` installs both) |
| Panel: check and build | `cd frontend && npm ci && npm run check && npm run build` |
| Panel: format | `cd frontend && npm run format` |

The store reports its changes through background tasks of the entry (`_publish` in `__init__.py`), and the first setup of a new database, as in every test, imports from the recorder as one too. A test that checks events, sensors or panel updates waits with `hass.async_block_till_done(wait_background_tasks=True)` after `store.async_flush()`, and flushes again before it reads the store.

## How it records

Each source listens to Home Assistant's `call_service` event and reads the calls; it never changes them. A source names its listeners (`listeners()`: event type, handler, filter); the integration registers them on the bus, and the import from the recorder replays old events through the same code.

- **notify** (`sources/notify.py`): legacy notify actions and `notify.send_message` on notify entities. A notify group calls the actions of its members right after its own call, in the same asyncio context; those calls are attached to the group's record instead of becoming records. The Companion app fires `mobile_app_notification_action` when someone taps a button, in the context of that person's user; the answer (action ID, user, time, `reply_text`) is attached to the latest notify record whose `data.actions` offered that action ID, a record that reached that user first. While a recorded call runs, `current_call` (a context variable) holds its record and channel; the Companion app catches a failed push and only logs it, so `failures.py` listens to the warnings and errors of `homeassistant.components.mobile_app.notify` and marks the record of the call it finds there *failed*, or for a member of a group that member, the group then *partial* or *failed* once all members failed. A call with the Companion app's tag (`data.tag`, a string) that reaches a Companion app (`recipients.companion_channels`: the legacy actions of `mobile_app`; notify entities take no data) ends the earlier notify records with that tag that are still *sent* and unanswered and whose Companion app channels (their own, or for a group the members it called) are all among those the call reaches, directly or through its group: a notification marks them *replaced*, `message: clear_notification` *withdrawn*, with its time and origin (`store.TagClose`, submitted to the worker before the new record, so it never matches that one). `clear_notification` with a tag becomes no record, nor do the calls a group makes for it, unless it also reaches a channel that is no Companion app and gets it as text. An excluded call ends nothing. Commands to the Companion app (`COMMANDS`, and every message starting with `command_` or `kiosk_`) become no record either, under the same condition, and end nothing; `message: TTS` is recorded as sent and replaces nothing; the panel shows `data.tts_text` like an announcement and the full-text search finds it (`NotificationRecord.spoken_text`). Only records sent up to the call change, as the recorder import replays older calls while recording runs; a live call during the import cannot end the older records the import adds after it. An index on the tag (`notifications_tag`, added by migration 7) serves this lookup and the tag filter of the list; a query has to spell the tag as `TAG_OF_ROW` does for SQLite to use it. A notification that fails afterwards leaves the earlier one replaced. An action that raises inside an automation or script leaves the error in the step of its trace: `traces.py` takes note of the run (origin `trace_key`, `run_id`) when a source hands the notification to the store (`on_add`, before the action runs), reads the trace through `trace.util.async_get_trace` whenever that automation or script writes its state, and fails the notification whose action and text match a step with an error, each step once; a run is forgotten once its trace reads stopped, or after a day.
- **The bell** (`sources/persistent.py`): `persistent_notification` reports a notification without the context of the call that created or dismissed it. Its services run right after the `call_service` event, in the same asyncio context, so the event listener leaves the call in a context variable for the update that follows; without one the origin is the integration that created the notification, as for any other call. On start the source catches up with what appeared or disappeared while it was not running. Creating an ID that is still open adds a record and marks the previous one *replaced*.
- **Telegram** (`sources/telegram.py`): the `telegram_bot` send actions with text (`send_message`, and `send_photo`, `send_video`, `send_animation`, `send_voice`, `send_document` with a caption, `send_poll` with its question). The chats come from the target's notify entities, from `chat_id` matched against the bot's allowed chats, or, with neither, the bot's first allowed chat, as Telegram does itself. Another action needs only an entry in `TEXT_FIELDS`. Messages sent with `notify.send_message` to the bot's notify entities are recorded by the notify source.
- **Speech** (`sources/speech.py`): `tts.speak` (recipients from `media_player_entity_id`) and `assist_satellite.announce` (target resolved with `helpers.target`: entities, devices, areas, floors, labels); media player groups expanded. Calls without text are skipped.

The origin comes from the trace context variable of the running automation or script (`origin.py`), the user from the call's context. Without either, the listeners still run inside the call, so `homeassistant.helpers.frame.get_integration_frame()` finds the integration that made it on the call stack: a custom integration becomes the origin with its name from the manifest, a built-in one counts as Home Assistant itself; this integration and `persistent_notification` are skipped, as they only pass the notification on. The view by origin groups integrations by their domain. Each notification keeps the name its origin had when it was sent; the WebSocket commands show the current one instead (`OriginNames`): the automation's or script's state or registry entry, the loaded integration, else the stored name. Each origin is looked up once per request, in memory, however many notifications it sent. Recipients of the bell and of announcements count for every user (`EVERYONE` in `notification_users`); Telegram chats belong to no user, so only administrators see them.

### Import from the recorder

When opening the store creates the database, as on first setup, the entry keeps `import_before` (the time before the sources started) and `importer.py` runs once in the background. It reads, read-only through `homeassistant.helpers.recorder.session_scope`, the recorder's `call_service` events of notify, `tts`, `assist_satellite` and `telegram_bot` and the `mobile_app_notification_action` events from before that time, with the `automation_triggered` and `script_started` events of the same contexts, in order of time, and replays them through the listeners of the enabled sources, giving the event loop a turn every hundred events; an event a source cannot handle is skipped and counted in one warning. The calls are found by the compact JSON of their data (`"domain":"notify"`), which works in every database the recorder supports; the query is two selects joined by `UNION ALL`, so each uses an index in SQLite, MariaDB and PostgreSQL. While replaying, `origin.replayed_origins` gives the origin from the recorded context: the automation or script that ran in it with the user who started it, else the user, else unknown, all marked `imported` (the panel says so in the details); integrations and trace links are not recoverable. Times come from the events, so notify groups join their member calls and answers go to a notification sent before them, as live. Inside `store.async_batch()` no change made by the import is reported one by one (a `ContextVar` marks what is submitted from its context); the purge runs and one `reload` refreshes open panels at the end. Notifications sent meanwhile are reported as usual, so automations get their events during the import too. `import_before` is removed when the import is done; an import cut short by a reload or restart deletes what it imported, with its counts, and starts over. The bell is not imported: Home Assistant creates most of its notifications without an event. The import reads tables of the recorder that are not part of Home Assistant's API; if they change, it logs a warning and the journal starts empty. Removing the integration deletes the database, its WAL and SHM files and the migration copies (`store.remove_database`), so a new setup imports again; a database of a newer version, which setup refused, stays.

## Automations

`automations.py` registers the action `notification_journal.query` once (`async_setup`), with `SupportsResponse.ONLY`: the filters of `notification_journal/list` (`websocket_api.FILTERS` and `filters`, shared by both; `services.yaml`, texts under `services` in `strings.json`), the records serialized as for the panel. The caller's user comes from the call's context and goes through the same rule as the WebSocket commands (`scope_of`): none (an automation) or an administrator sees everything, any other user what the panel shows them, and with *Nothing* for non-administrators the call raises `Unauthorized`. The archive is left out, as it belongs to a user's view.

The events are fired where the store's changes reach the panel (`_publish` in `__init__.py`): `added` fires `notification_journal_recorded`, `failed`, which `mark_failed` reports instead of `updated`, fires `notification_journal_failed` and reaches the panel as an update. Both carry `automations.event_data`. What the import from the recorder records inside `store.async_batch()` is not reported, so it fires nothing.

`sensor.py` adds *Notifications today* and *Failed today* under one service device (state class `total`, `last_reset` local midnight). Their `DataUpdateCoordinator` (`today.py`) is created and read first in `async_setup_entry`, so a failing read retries the setup, and shut down before the store closes; without an interval, it reads the counts of the view of administrators since local midnight from `notification_counts` (`store.async_counts_since`), again after every change the store reports (its debouncer bundles them) and at midnight. The events give recipients and origins their current names, as the panel does.

## Database

`notification_journal.db` next to `configuration.yaml`, SQLite with FTS5, accessed from one worker thread so writes keep their order, in WAL mode with `synchronous = NORMAL` as the recorder uses for SQLite; during a backup the worker waits. `SCHEMA` in `store.py` is the current state for a new database. A schema change raises `SCHEMA_VERSION` and adds a step to `MIGRATIONS`, from the previous version; on open, the store copies the database to `notification_journal.db.bak-v<version>` and runs each missing step in its own transaction. Every open removes the copies of earlier migrations, and the copy of the latest one once it is older than `MIGRATION_COPY_DAYS` (7): by then the migrated database has proved itself, and the copy would otherwise take as much space as the journal in every Home Assistant backup. A database of a newer version is left untouched and the setup fails (`tests/test_migrations.py`). A step is an SQL statement or a function that gets the connection, like `_fill_counts` in version 5; version 7 adds the index on the tag.

### Statistics

The statistics read only `notification_counts` (`statistics.py`): one row per quarter hour, origin and view, with the number of notifications, how many offered buttons, how many were answered and how many failed in whole or in part; no texts. Quarter hours, because every time zone is a whole number of them away from UTC, so each row lies within one local hour, day, month and year, also at +5:30 or +5:45. The view is `""` for administrators (every notification once), `*` for the bell and announcements, or a user id; a user's statistics add their rows to those of `*`, so a notification that also reached everyone counts only under `*`. A user's row counts only that user's answer, the row of `*` none, as in the panel. The origin is `origin_key` of the notification (`origin.origin_key`, indexed with the time): the automation or script, `integration.<domain>`, or the kind; the view by origin, the origin filter and the facets use it too.

Every change to a notification moves its counts from what it was to what it is (`store._recount`): when it is recorded, when a group's call adds recipients, when an answer arrives and when it is marked failed. Deleting, archiving or purging a notification leaves them alone. A burst is a quarter hour in which one origin sent at least five notifications to the view that is read; it is found when the statistics are read, so it is right for every view, a user's together with `*` included. Migration 5 adds `origin_key` and fills the counts from the stored notifications, a quarter hour at a time so its memory does not grow with the journal (`tests/test_statistics.py` checks that filling and counting as they come agree); migration 6 adds `failed` and counts the notifications already marked failed, unless the step to 5 just created the column and counted them, and adds `resent_from` to the notifications. The purge keeps the counts for whole calendar years (option, at least two, so a year can be compared with the one before) and never shorter than the notifications.

The command `notification_journal/statistics` builds the period in the caller's time zone, loaded without blocking (`statistics.period`): a day in hours (23 or 25 when daylight saving time changes), a week from the user's first weekday or a month in days, a year in months. It reads the period by quarter hour and origin and the part compared with by origin only (notifications and failed ones), each through the primary key, and sums them up outside the event loop. The comparison covers as much of the period before as has passed of this one and is only offered (`comparable`) when counting had started by then.

## Panel

TypeScript with [Lit](https://lit.dev), bundled by esbuild into `custom_components/notification_journal/frontend/panel.js`; the bundle is not committed, the CI and the release build it. It uses only the theme's CSS variables (no colours or fonts of its own, so every theme applies, light and dark; charts take `--graph-color-N`, else `--color-N`, as Home Assistant's own), the `hass` object Home Assistant passes in and `ha-icon` (for the icons of automations and scripts, with an own fallback), no other frontend components, so it does not break when those change. The integration serves the scripts (`panel.js`, `iconset.js`) itself with `Cache-Control: no-cache`, so a new panel reaches the browser on the next load without a restart.

The export (`export.ts`) pages through `notification_journal/list` with the list's filters and the caller's permissions, 200 records at a time, and builds the file in the browser, so it needs no command of its own and no single large message. JSON holds the records as the API returns them; CSV has one row per notification, with recipients, failed calls and answers joined in one column each, a byte order mark for spreadsheets, and a leading apostrophe on a cell that starts like a formula.

The panel subscribes to `notification_journal/subscribe` without the frontend's automatic resubscribe, which loses a subscription the server refuses on reconnect, as while Home Assistant starts. After each reconnect (the connection's `ready` event) it subscribes anew and, once that succeeds, loads the list, the filter choices and the statistics anew, since what was sent meanwhile never arrived; a refused subscription is tried again every 5 seconds.

Media of a notification (`media.ts`) come from the Companion app's `data`: `image`, `video`, `audio`, and an iOS `attachment` by its content type or extension. Only addresses `safeUrl` (`markdown.ts`) accepts are loaded: http(s) or a path on this Home Assistant, as for links. A path on this Home Assistant is signed first (`auth/sign_path`, valid for an hour), as camera and media views need a login the browser does not send for images and videos. A video shows the notification's image, else its first frame (`preload="metadata"`, `#t=0.1` for Safari, loaded once the card is near the screen), and plays in the card on a click; whatever cannot be loaded falls back to a link. A click on an image opens it in an overlay, a native `<dialog>` rendered next to the card, dimmed the way Home Assistant dims its dialogs (`--ha-dialog-scrim-backdrop-filter`).

The panel is registered with `frontend.async_register_built_in_panel` as a custom panel, because `panel_custom.async_register_panel` cannot hide it from the sidebar. Changed options reload the entry, which registers the panel anew.

The icon (`custom_components/notification_journal/brand/`) is drawn in `icon.svg`, which the README also shows beside its title; the PNGs are rendered from it with `magick -background none -density 192 icon.svg -resize 256x256 icon.png` (and `-density 384 … 512x512 icon@2x.png`). The sidebar shows the same motif as a single-colour 24 px icon, `notification_journal:bell-stack`, from the icon set in `frontend/src/iconset.ts`; Home Assistant loads that script with every frontend (`frontend.add_extra_js_url`).

The screenshots in `docs/screenshots/` are rendered from made-up data with a mock Home Assistant in headless Chromium (`scripts/screenshots/`): build the panel, then `scripts/screenshots/render.sh`. `render.mjs` fixes the clock to Saturday, 21 November 2026, 16:40 UTC, so the mock data (`readme-data.js`) and the timestamps in the camera snapshots fit together. The page `readme.html` carries the colours of the Nordic theme (`nordic-blue`), resolved from its YAML; `frame.html` puts the raw shots into a browser window and composes `hero-nordic-*.png`, the README's opening picture, from the timeline and the phone. It also composes `social-preview-nordic-light.png`, the repository's social preview for link previews (1280 × 640); GitHub takes it only by hand, so a changed one is uploaded under *Settings → General → Social preview*. The README shows each picture through `<picture>` in the light or dark variant that matches the reader's GitHub mode. The files carry the theme in their name (`<view>-nordic-<mode>.png`): a new look gets new names, because browsers keep showing a cached picture under an old one.

## WebSocket API

The panel reads the journal through these commands. An administrator sees every notification; any other user only those that reached them (a notification counts for a user when one of its recipients, the members reached through a group included, is that user's person), those under the bell and announcements, or nothing when the option says so. A record carries `status_time` and `status_by` (an origin) once it was dismissed, replaced or withdrawn, `source_ref`, the ID of the notification under the bell, and `answers`, the buttons tapped; a user who sees only their own notifications gets only their own answers.

| Command | Returns |
|---------|---------|
| `notification_journal/list` | `records` and `total`; filters `text` (full-text, prefix match), `channel` (action or group), `origin` (the key of an origin, as in `facets`), `status` (`failed`: failed in whole or in part; `answered`: with an answer, for a user limited to their own notifications one of theirs), `tag` (the Companion app's `data.tag`), `since`, `until`, `user_id` (administrators only), `newest_first`, `group_by: origin` (sorted by origin, then time; adds `groups`, the number per origin), `archived` (the caller's archive instead of the active view), `limit` (≤ 200), `offset`; with `days: true` the first page adds `days`, every day that holds matches with `since`, `until` (local midnights) and `count`, in `time_zone` (default Home Assistant's) and in the order of the list |
| `notification_journal/get` | one record by `record_id` with its data, the calls a group made and `trace_path`, the link to the exact run of the automation or script |
| `notification_journal/facets` | `origins`: the origins that sent notifications the caller may see, by key (automation or script, `integration.<domain>`, or `user`, `system`, `unknown`) and current name (else the one stored with the newest notification; none for the kinds), for the origin filter |
| `notification_journal/statistics` | the statistics of a `period` (`day`, `week`, `month`, `year`) `offset` periods back, with weeks starting on `first_weekday` (0 Monday to 6 Sunday) in `time_zone` (default Home Assistant's): `start`, `end`, `totals` (with `previous`, the same part of the period before), `buckets` per hour, day or month with the counts per origin, `heatmap` (weekday from Monday × hour), `origins` with their name, counts and trend, `has_older`, `comparable` (counting had started at the start of the period compared with), and `kept_since`, the oldest single notification still kept; a user who is no administrator gets their own view, administrators any with `user_id` |
| `notification_journal/subscribe` | an event `{change: added \| updated, record}` for every new or changed notification the caller may see, `{change: removed, record_id}` for a deleted one, `{change: reload}` when many changed at once (import, purge) |
| `notification_journal/resend` | sends a failed or partly failed notify notification again (administrators only): to each failed member of a group once, else as it was; notify entities get `send_message` with text only, a legacy action the stored text and data plus what the legacy groups on the way add to a member's call (`recipients.member_defaults` with the group's own `add_defaults`). Each call runs through Home Assistant with its own context, registered in `sources.notify.resend`, so the notify source records the call made in that context by hand with `resent_from`, apart from any group call before; tasks started meanwhile have contexts of their own. A call that raises fails its new notification; the errors come back joined as `home_assistant_error` |
| `notification_journal/archive` | archives `record_ids` (≤ 200) for the caller, or restores them with `archived: false`; only the caller's view changes, a user who is no administrator only archives what they may see; returns `changed` |
| `notification_journal/delete` | deletes one notification by `record_id` for every recipient; administrators only, not used by the panel |

## CI and releases

The CI (`.github/workflows/ci.yml`) runs on every pull request and on `main`: lint and tests in `python:3.14-slim`, the panel's type check and build in `node:26-slim`, and Home Assistant's `hassfest` and the HACS check. Renovate keeps the tools, images and actions current. Branch names contain no `tags/` and do not end in `tags`, or the HACS check fails: HACS strips `tags/` from a branch's download address, and a name ending in `tags` puts `tags/` into it as well.

Releases come from release-please (`.github/workflows/release.yml`, `release-please-config.json`). Pull requests are squash-merged with their title as the commit subject and their description as its body (repository setting), so release-please also reads the footers in the description, wherever they stand. A `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block added to a merged pull request's description replaces its commit message for the version and the changelog from the next run of the workflow on; `.github/workflows/pr-title.yml` checks each title for a Conventional Commit type and one of the listed scopes, and the ruleset of `main` requires that check (`Conventional PR title`). From these subjects on `main` release-please keeps a release pull request (`chore(release): <version>`) with the next version and the changelog up to date, in which only `feat`, `fix`, `perf` and `revert` appear (sections in `release-please-config.json`); merging it tags the version, writes it into `manifest.json` and publishes a GitHub release. release-please acts as a GitHub App (repository variable `RELEASE_APP_CLIENT_ID`, secret `RELEASE_APP_PRIVATE_KEY`; permissions: contents and pull requests, read and write), because changes made with the workflow token start no workflows: that way the CI runs on the release pull request, and the published release starts the archive job. That job builds the panel and attaches `notification_journal.zip` (the contents of `custom_components/notification_journal/` with the built `panel.js`), which the Marketplace installs (`hacs.json`: `zip_release`). Every release is tested as a beta first: push a tag `v<next version>-beta.<n>` (e.g. `git tag -a v0.1.0-beta.1 -m v0.1.0-beta.1 && git push origin v0.1.0-beta.1`): the workflow publishes it as a pre-release with the same archive (`scripts/package.sh` packs both) and notes in the form release-please gives a release (`scripts/beta_notes.py`, which reads the commits themselves: it sees a breaking-change footer only at the start of a line and no override block): a block for this beta with what changed since the beta before it, else since the last release, and below it one for each earlier beta of the version, in the sections of `release-please-config.json`; only those who turn on pre-releases for the repository are offered it. The notes are not written into `CHANGELOG.md`, which holds releases only. release-please leaves these tags alone, and the pre-releases stay after the real release. The release pull request is merged only once a beta with everything it contains has been tested on a Home Assistant installation. `hacs.json` hides the default branch, so the Marketplace never offers the unbuilt branch as an update.

## Issues and discussions

The issue forms in `.github/ISSUE_TEMPLATE/` take bugs and ideas; questions go to the discussions (repository setting), whose Q&A category has the form `.github/DISCUSSION_TEMPLATE/q-a.yml`. The form's file name is the category's slug, `q-a`, and the issue chooser, `README.md` and `CONTRIBUTING.md` link to it: renaming the category detaches the form and breaks the links.

## History of the name

The integration started as `notification_history`, a domain that already belongs to another integration in the HACS catalogue, and was renamed to `notification_journal` before its first release.
